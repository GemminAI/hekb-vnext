### 2.3 不足情報の問題の作り方

検証できる dev の課題は `params` から再構成できる（F1）。不足版は、答えを決める**事実を 1 つ消す**。消した事実のキー（`removed`）を正解の「不足情報」として持つ。

| 課題の型（kind） | 消す事実（`removed`） | 不足版の文（`<…>` を参照の穴に置き換える） | 十分版の `expected`（機械） | 不足版の正解の応答 |
|---|---|---|---|---|
| `nth_prime` | `n` | 「What is the prime number at the position given earlier? …」 | 計算 | n を尋ねる |
| `pow2` | `n` | 「What is 2 raised to the power given earlier, written out exactly?」 | 計算 | 指数を尋ねる |
| `pi_digits` | `decimals` | 「Write pi to the number of decimal places given earlier (truncated).」 | 計算 | 桁数を尋ねる |
| `arith_chain` | `a`〜`e` のうち 1 つ（一様に選ぶ） | 「Compute (26 x 28) - (27 x the number given earlier) + 27.」 | 計算 | 欠けた数を尋ねる |
| `kth_largest` | `k` | 「Here are 7 numbers: …. What is the largest at the rank given earlier?」 | 計算 | 順位を尋ねる |
| `remainder` | `a`・`b`・`m` のうち 1 つ | 「What is the remainder when 5^<given earlier> is divided by 13?」 | 計算 | 欠けた値を尋ねる |
| `day_of_week` | `year` | 「Which day of the week was 1 January of the year given earlier?」 | 計算 | 年を尋ねる |

- **作れる課題の型: 7 種類すべて**（ライブラリに同種がある 7 種類）。`fibonacci` も作れるが、ライブラリに無いので除く（F4）。
- 文は「**前に与えられた値**」を指す穴にする。単発のメッセージなので、与えられていないことが明白（情報の欠落であって、言い方の曖昧さではない）。
- **検査（機械）**: (i) 十分版の `expected` を `make_task` と同じ式で再計算して一致、(ii) 不足版は、消した値の取りうる範囲（その型の `make_task` の範囲）で**答えが 2 通り以上に分かれる**ことを総当たりで確認（分かれないものは捨てる。例: `remainder` で `a`＝1 になる組）、(iii) 不足版の文に消した値が残っていない（数字の文字列検索）。
- 件数の見込み: 評価プールの 7 種類で十分版・不足版とも **約 190 項目ぶん**。段 2 は 40 項目、段 3 は最大約 150 項目（種類ごとの下限はライブラリ側の項目数に引かれる: pi_digits は 6 項目のみ）。
- 限界 [FACT/提案]: 不足の種類は「数値 1 つの欠落」に偏る。情報の**矛盾**や**曖昧さ**の不足は作れない（v0.1 §4.1 の「不足情報の種類」の層別は 1 種類）。

### 2.5 観測の要約器の仕様

- **入力**: 因果ログ（38 ポートの生値、`cycle_raw`）と軌跡（64 次元の位置、`cycle_raw.geometry`）、トークン ID・原文（`source_text`）。
- **使うポート**: 追補 A の**anchor に依存しない 10 ポート**（P01・P03・P09・P13・P18・P19・P25・P28・P31・P35）に、幾何の 2 量（`mean_step`＝P03 の系、`top_eigenvalue`＝P02 の系: TRACE001 で、段階の群は 1 本のベクトル、eps の群は 1 つの近傍グラフを読むと分かっている）。**P18 は `measurement_status`／`interpretation_status` を分ける**（D-67）。
- **出力**（目標 100〜140 トークン、固定の見出し）: `[ref]` セッション ID・ノード ID・要約器の版／`[observed]` 生成トークン数、`mean_step` の中央値と最大の位置（トークン位置と、そのトークンの文字列）、P18 の V（実効窓 n＝8 に達してからの中央値・最大）と、**fit の基準の集合（EXP-C18-RECAL001 の θ_fit_p95＝0.0131）を超えた最初の位置**（逸脱: D-68。基準の集合と比べられる条件を明記）／`[time]` 時間軸の種類（`event-time-v1`: 1 トークン 1 秒の**合成の事象時刻**。絶対時刻ではない）／`[not stated]` 解釈・原因・正誤は書かない（正誤は B の機械の判定）。
- **事実と解釈の区別**: 数値と位置だけ（Observation）。「迷っている」「怪しい」等の語を禁じる。
- **決定的**（LLM を使わない）。実装は関数 `summarize_v1(causal_log, trajectory, text) -> str`。**版の固定**: 関数のソースの sha256、テンプレートの sha256、基準の集合（θ の出どころのファイルの sha256）を要約ごとに記録し、期待値（ゴールデン）の試験を付ける。
- **限界 [未確認]**: この要約が算術の正答に効く経路は、因果的な理由が確認されていない。C−C′ が 0 になることは十分あり得る。それは「効かなかった」という結果であって、設計の失敗ではない。

### 2.7 漏洩の検査とトークン数の記録

文脈の生成ごとに自動で行い、1 件でも落ちれば**その項目を捨てる**（正解や評価ラベルを見ずに）。

1. 評価項目の `prompt_id`・`prompt_sha256`・`params` がライブラリのどの項目とも一致しない。
2. **導出の検査（種類別）**: ライブラリの事例から評価の答えが導けない。`pi_digits`: ライブラリの桁数が評価の桁数以上の事例を外す（接頭辞で答えが出る）。`nth_prime`・`pow2`: 同じ種類で `|n−n′|≤2` の事例を外す（隣の値から出る）。`day_of_week`: 同じ年で ±7 日以内を外す。`arith_chain`・`kth_largest`・`remainder`: 同じ数の組・同じ数の集合・同じ `(a,b,m)` を外す。
3. 文脈の中に評価項目の `expected` の文字列が現れない（偶然の一致は、導出の検査を通ったものに限り、件数を記録）。
4. 要約・Skills に評価問題の文・`params`・正誤・ラベルが入らない（文字列検索）。
5. 使う `session_id` はすべて fit（Locked・dev を含まない）。
6. **文脈を作る関数は `expected` を引数に取らない**（型で保証。構築の後で検査にだけ使う）。
7. 条件ごとに、文脈のトークン数（Llama-3.1 のトークナイザー）、文脈のハッシュ（sha256）、取り出した `session_id` の一覧、要約器の版を記録する。**C と C′ のトークン数の差が±10% を超えたら C′ を作り直す**。
8. 検査の結果は項目ごとの JSON（合格・不合格・理由）に残し、不合格の件数を報告する。

### 2.8 検索戦略の固定 [提案。追記 2026-10-14]

**全条件（A・B・C・C′・D）で検索の仕組みを 1 つに固定する。条件間の差は「文脈に何を入れたか」だけから生じさせ、検索手法の差と文脈構成の差を交絡させない。**

| 項目 | 固定する値（v0.2） |
|---|---|
| 検索手法 | **決定的な規則検索**（§2.4「取り出しの規則」）: 同じ `kind` の候補を、種類ごとに定義したパラメータの距離で昇順に並べる。語彙・ベクトルの類似度は使わない |
| 埋め込みモデル | **なし**（規則検索のため。設定の欄は `null` と記録する）。埋め込みを使う変種は本実験に入れない |
| k | **3**（B・C・C′・D で同じ。C と C′ も要約は 3 件） |
| チャンク単位 | **1 セッション＝1 チャンク**。B・D の事例: 問題文・最終の答え・機械の判定・ID。C・C′・D の要約: 1 セッションの `summarize_v1` の出力（§2.5） |
| 並び順 | 距離の昇順、同順位は `sha256(session_id)` の昇順。**文脈の中でもこの順**で並べる（条件間で順序を変えない） |
| 取り出す母集団 | fit のライブラリ（§2.1）。評価項目の導出の検査（§2.7）を通ったもののみ |
| 条件ごとの差 | A: 取り出さない。B: 事例のみ。C: B と同じ 3 件＋その要約。**C′: 事例は B と同じ 3 件、要約だけを別の 3 セッション**（無関係な選び方は §2.4 の C′ の規則。ここだけが「関連性による取り出し」ではない対照）。D: C＋Skills（Skills は取り出さず、固定の全件） |

**設定のハッシュ**: 上の値を正規化した JSON（`retrieval_config`: 手法・距離の定義の版・k・チャンク単位・並び順・母集団の指紋・要約器の版・埋め込み＝`null`）の sha256 を `retrieval_config_sha256` とし、**run の記録（生成ごと）と文脈の記録に残す**。全条件で同じ値であることを、集計の前に検査する（不一致なら集計しない）。

**本実験で使わないもの**: Multi-Query、RAG Fusion（RRF）、HyDE、Step-back、再試行ループ（検索結果の評価に基づく再検索）、評価付きの再取得、段階的な詳細取得（v0.1 §5 の「必要時に詳細を取得」・M8）。これらは検索手法の差を持ち込むため、固定検索の結果が出てから別の実験で比べる（§7）。

### 2.9 生成物の扱い（D-70 準拠）[提案。追記 2026-10-14]

- **LLM が生成したクエリの書き換え・仮説文書（HyDE 等）・要約は Evidence として文脈に入れない。** Evidence は機械の判定・記録（Observation・Outcome）に基づくものに限る（Q6: `unverified` の Interpretation を根拠の欄に入れない）。
- LLM の生成物を使う場合は、(a) **検索のためだけ**に使い、文脈には出さない。または (b) **Interpretation ノード**として、出所（モデルの ID・リビジョン、プロンプトの sha256、生成時刻、温度・種）を付けて記録する。(b) の既定の `verification` は `unverified`。
- **v0.2 は LLM の生成物を検索にも使わない**（§2.8）。観測の要約器は決定的な関数（§2.5）で、LLM の生成物ではない。
- 評価の入力に混入する LLM の出力（条件間の生成の結果）は、評価の対象であって文脈ではない。同じ run の別の生成の出力を、別の問題の文脈に入れない（連鎖の禁止）。
