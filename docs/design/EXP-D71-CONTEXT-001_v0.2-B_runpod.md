## 3. 因果ログの照合（段 3 の中心）[提案。事前登録の草案]

### 3.1 問い（D-68 の語）

条件ごとの新しい軌跡を、ライブラリの経験の軌跡（INFO001 の fit）と、また条件どうしで比べる。**「異常」「ハルシネーション」は評価の層の語で、計器の出力には使わない**（D-68）。計器の量は次の 2 つの幾何の量と P18。

| 語 | 定義（操作的） | 比べるもの |
|---|---|---|
| **変動**（基準なし。1 本の軌跡の中） | **V**: 生成トークンのうち実効窓 n＝8 に達したもの（P18 `result.n == 8`）の `v_norm` の中央値（計器としての較正は EXP-C18-RECAL001 の範囲）。**S**: 同じトークンの `mean_step`（P03）の中央値 | 条件間（C と C′ など。項目単位の対応あり） |
| **逸脱**（基準の集合と比べられる条件が要る） | **D**: 実効窓 n＝8 のトークンのうち、80 次元の窓の特徴（anchor に依存しない 10 ポート × 8 トークン。`index/experience_index.py` の特徴）が、基準の集合の k 近傍距離（k＝5）の 95 分位を超えた割合。**D_final**: 最終行の前の 16 トークンのみ | 基準の集合: ① **同じ実行の条件 A の十分版で機械が正答と判定した生成**（同じ種類。**項目を 1 つ抜く**）。② 副次: INFO001 の fit（同じ種類）。②は `space_id` と方針の指紋（`policy_set`）が一致し、システム指示・生成の設定が同じ場合に限る（B0 で確認）。違えば逸脱とは呼ばず「別の空間の距離」と記す（Q6） |
| **分岐**（共通の過去を持つ複数の軌跡が要る） | **τ_text**: 同じ項目・同じ種の 2 条件の生成で、トークン ID が最初に異なる位置。**τ_geo**: 64 次元の位置の距離が、**同じ条件のサンプル間（R=3）の同じ位置の距離の 95 分位**を最初に超える位置。共通の過去は「問題文を共有する」だけで、**文脈は条件で異なる**（隠れ状態は文脈全体に依存する）。したがって「分岐」は**文脈の違いによる出力の分かれ**であり、ONSET002 の分岐点の再サンプリング（接頭辞を固定）とは別の量 | 条件の組（C と C′、B と C など） |

**幾何の確認（登録済み、ゲート）**: S と eps 近傍グラフの量を、保存された 64 次元の位置から**カーネルを介さずに**再計算し、保存値に一致すること（スカラーは |差|≤1e-9、Betti 数は等号）。不一致なら主張は「ポートについて」になり、そのように報告する（ONSET002 rev 1 と同じ）。

### 3.2 仮説の例（方向は期待であり、検定は両側）

不足版の問題（情報が欠けている。D-70 の「不足情報の候補」を介入で確かめる Q8 に近い）で、

- **H-V**: C は C′ に比べ、V が異なる（期待: C で V が小さい＝変動が小さい）。
- **H-D**: C は C′ に比べ、D_final が小さい（通常の束に収まる）。
- **H-B**: C は C′ に比べ、τ_geo の中央値が大きい（分岐が遅い／起きない）。
- **H-S**: C は C′ に比べ、S が異なる。

十分版は**陰性の対照**: 同じ対比を十分版で見て、不足版と同じ大きさで動くなら、効果は「情報の欠落への対応」ではなく文脈の内容の一般の効果として読む。

### 3.3 判定の基準・多重比較・止まる条件 [提案。段 2 の後に δ を固定して版を上げる]

- **単位**: 項目（R=3 サンプルの平均）。対応あり。**項目単位のブートストラップ**（2,000 回、種を固定）。折りはなし（予測ではなく差の推定）。
- **成功（確認）**: 95% 区間の下限／上限が 0 を含まず、かつ |Δ| ≥ δ。**行動の指標（M1・M2）**: δ_M は段 2 の結果で決める（空欄）。**幾何の量（V・S・D・D_final・τ）**: δ_T ＝ 項目間 SD の 0.25 倍（SD は、ポッドの最初に実行する**別の 20 項目・条件 A のみ**の較正の生成から求め、主実行の結果を見る前に版に書く）。
- **多重比較**: 2 つの族を分ける。**行動の族**: {M1, M2} × {B−A, C−B, C−C′, D−C} の 8 検定、Holm（α＝0.05）。**幾何の族**: {V, S, D_final, τ_geo} × 対比 C−C′（不足版）の 4 検定、Holm（α＝0.05）。他の対比・指標・十分版は**探索**（報告するが確認と呼ばない）。
- **効かなかった場合**: 区間が広いときは「検出力不足」と書く。効果がないことの証明とは扱わない（v0.1 §10.1）。
- **判定保留**: 幾何の確認の不合格、空間の不一致（`space_id` が INFO001 と違う）、採点不能（`ANSWER`・`CLARIFY` のどちらも無い）が 10% 超。
- **欠測**: 生成の失敗・取り込みの失敗は項目ごと除外せず、**条件ごとの失敗率**を報告し、全条件で揃えた感度分析（失敗した項目を全条件から外す）を併記。
- **止まる条件**: (1) 幾何の確認が最初の 20 件で不合格、(2) 決定性の検査の不合格（同じ入力・同じ種で隠れ状態が再現しない）、(3) 取り込みの冪等性（同じ生成を再取り込みして `object_id` が変わる）、(4) 文脈の sha256 が Mac の値と一致しない、(5) ポッドの GPU の機種・版が §1 と違う、(6) Locked に触れる必要が出た、(7) メモリ・ディスクの上限。
- **結論の書き方**: 「観測要約が有効／無効」と一括せず、どの種類・指標・条件で、と限定する。

**費用**（RunPod の現在の価格は未確認。A100 80GB／H100 の 1〜2 USD/時間と仮定）: Pod の時間＝環境構築 0.5 時間＋B0・較正 0.5 時間＋D71 約 1 時間＋ONSET002 約 3 時間＋予備 ×1.5 ＝ **約 7〜8 時間 → 約 7〜16 USD**。ネットワーク・ストレージ 50〜100 GB の数日分は数 USD。**GPU の機種は A100 80GB またはそれ以上を推奨**（バッチ 10 × 約 2,000 トークンの KV と bf16 の重み 16 GB が余裕で入る）。MSD0001 は機種が記録されていない（G2）ため、**今回は機種を記録して比較できる状態にする**。

## 5. ポッドの運用 [提案]

- **鍵とトークン**: RunPod の API キー・HF のトークンは **Tomo が作り、環境変数（名前のみ記す: `RUNPOD_API_KEY`・`HF_TOKEN`）で渡す**。値は設計書・ログ・コミットに書かない。ハーネスは環境変数を読むだけで、値を出力しない。
- **Pod の作成と終了は Tomo が行う**。ハーネスは Pod を作らず、終了もしない。終わったら Tomo が**終了・削除**する（過去の運用で、停止記録の無い Pod がある: `ledger_v3.md`）。ストレージ（Network Volume）に残す場合は、残す理由と削除の期限を記録。
- **持ち帰り**: 出力は Pod の外に必ず出す（G9: 出力が Mac に無い Pod がある）。手順: Pod 上で `manifest.json`（全ファイルの相対パス・サイズ・sha256）を作る → `runpodctl send`／`rsync` で Mac の `/Volumes/SSD1TB/d71_work/pod_out/` に取得 → Mac で sha256 を全件照合 → 一致を `transfer_verified.json` に記録 → その後に Pod を終了。**照合が済むまで Pod を終了しない**。
- **記録**: Pod ID（`RUNPOD_POD_ID`）、作成・停止の時刻、GPU の機種、ドライバ。終了後に RunPod の**監査ログ**（`audit-logs-*.csv`）を取得し、作成・開始・停止の時刻を生成の時刻（UTC）と突き合わせて `pod_runtime_correlation.csv` に残す（RUNPOD-INVENTORY001 と同じ形式）。
- **置き場所**: コード・仕様は git（`nvs-runtime/examples/d71_*`）。結果・出力は git の外（`experiment-evidence/EXP-D71-CONTEXT-001/stage3/`、`/Volumes/SSD1TB/d71_work/`）。
